## What shipped, and what did not

| Stage | Does | State |
|---|---|---|
| **A** | Active units at `Location = Livraison` with a delivery date → `Item Status = Delivered`, `Delivery Status = Completed` | **live logic, ready to deploy** |
| **B** | *(was: touch rows so calculated columns re-evaluate)* | **dropped — see below** |
| **C** | Counts `Delivered`/`Cancelled` rows older than the grace period | **report only, deletes nothing** |

### Why stage B was dropped

Two measurements, both against the 2026-09-11 04:10 export of `Order Items`:

1. **There is no column to refresh.** `Order Items` has no `Estimated Delivery Date`,
   and no calculated column at all. Roadmap item 20 says the column is *buildable*,
   not built.
2. **The planned filter barely filters.** `calculated-columns-plan.md:548` claims
   narrowing to Active + both delivery-date columns null "cuts the work by roughly
   50×". It cuts it **1.3×** — 915 of 1,189 rows. An Active unit has no delivery
   date by definition, so that clause removes nothing. 915 writes a night is
   ~334,000 versions a year and ~1,830 Power Automate actions per night, which on
   a 2,000/day allowance leaves nothing for the five event-triggered flows.

When the column is actually built, the choice is: a **plain column this flow owns**
(computed in the flow, written only on change — the `needsUpdate → If → Patch` shape
the N3 flows already use), or **not stored at all** (computed in Power Query for the
viewer, DAX for Power BI). Deciding question: does anyone need to sort or filter a
SharePoint view by it? Yes → plain column. No → compute it in the consumers.

## The rule stage A implements

> Delivery is real ⟺ `Location = Livraison` **and** a delivery date is entered.

The user's own, 2026-09-08. Already encoded in `x1_clear_fabricated_stages.js` and
`x2_set_delivered.js`; this flow is the forward-looking version of X2.

Two guards, both from X2's own experience:

- **Only `Active` rows are promoted.** A `Cancelled` or `Regrouped` unit sitting at
  Livraison is a human decision and is left alone.
- **Future delivery dates are held back, not written.** X2 excluded 21792-3/5 and
  21792-4/5 for exactly this — archive delivery date 2026-09-24, in the future.
  Neither is Delivered today, so the first time someone types that date on the live
  row this flow would otherwise flip it. Instead it composes
  `A5_Held_back_future_delivery_date` in the run history and moves on.

## Part 1 · Deploy

Same route as the N3 flows (`n3-deploy-and-test.md` Part 1) — Power Automate has no
"import definition" for a new flow, so: build a shell, then overwrite its definition.

1. **Create → Scheduled cloud flow.** Name it exactly `Nightly Cleanup`.
   Set the recurrence to **daily**; the pasted definition sets 01:00 Eastern.

2. **Add one SharePoint action to the shell and configure it** — Site Address
   `https://ermcopower.sharepoint.com/sites/PioneerPlanificatio`, List `Order Items` —
   then save.

   🔑 **Not cosmetic.** The pasted JSON refers to its connection by *name*
   (`"connectionName": "shared_sharepointonline"`), which resolves through a binding
   the **shell** carries, not through anything in the definition. Paste into a shell
   that never had a configured SharePoint action and every action comes back unbound.

3. **Export the shell's JSON and intake it before pasting anything:**

   ```bash
   mkdir -p "workflow-data/nightly-cleanup/_inbox"    # drop the JSON (and .zip) here
   python scripts/flow_version.py --flow "nightly-cleanup" intake --all \
       --note "empty shell, scheduled trigger, SharePoint action configured"
   ```

4. **Paste** `Nightly_Cleanup.definition.json` into the extension's definition pane,
   keeping the shell's `{connectionReferences, definition}` wrapper — replace only the
   `definition` value. Save.

5. **Leave the flow OFF** until the Part 3 test passes.

## Part 2 · The trigger-flow interaction

Every stage-A write fires the `Order Items` create-or-update trigger flow once.

At current volume that is **0–5 runs a night**, which is noise, not a problem — this
is only worth solving if the number ever grows. If it does, put a *trigger condition*
on that flow (evaluated before a run is created, so it costs nothing, unlike a
first-action Condition which still consumes a run):

```
@not(equals(triggerOutputs()?['body/Editor/Email'], '<the flow owner account>'))
```

## Part 3 · Test — one row, reversible

Stage A changes nothing today, so make it something to change.

1. Pick one **Active** unit not at Livraison. Record its current `Location`,
   `Item Status`, `Delivery Status`, `Delivery End Date`.
2. Set `Location = Livraison` and `Delivery End Date =` **yesterday**.
3. Run the flow manually.
4. **Expect:** `A4_Mark_delivered` ran once; the row now reads `Item Status =
   Delivered`, `Delivery Status = Completed`; `Location` and `Delivery End Date`
   unchanged (the flow deliberately does not rewrite what it did not compute).
5. **Now the guard test.** Reset the row to your recorded values, then set
   `Location = Livraison` with `Delivery End Date =` **tomorrow**, and run again.
   **Expect:** `A3` takes the *else* branch, `A5_Held_back_future_delivery_date`
   composes with that unit's Title, and **no write happens**. The row stays `Active`.
6. Restore the row to its recorded values.

⚠️ **A zero-item loop is not a pass.** If `A2` reports *"Skipped — there are no items
to repeat"*, `A1` matched nothing and the test proved nothing. That is the same
false-pass that cost a run during N3 testing on 2026-09-10 — it looks almost identical
to a real pass in the run graph. Check `A1`'s output count before believing step 4.

## Part 4 · Stage C, and what it is waiting on

`C1` lists rows older than `GRACE_DAYS` (**7** since 2026-09-16, was 30 — set at the top
of the generator). `C2` composes the count. **Nothing is deleted.**

**The clock is `DeliveryDate` — the list's `Delivery End Date` — not `Modified`**, decided
2026-09-16. `Modified` recorded when a row was last *touched*; `DeliveryDate` records when
the unit was *delivered*, and housekeeping never rewrites it. Stage A keys on the same
column, so the two stages agree by construction.

⚠️ **`Cancelled` rows still ride on `Modified`, and have to.** A cancelled unit was never
delivered and carries no delivery date — 73 of the archive's 116 `AN` units have none — so
a `DeliveryDate` filter would match no cancellation, ever, and the count would silently
omit them. Hence two halves:

```
(ItemStatus eq 'Delivered' and DeliveryDate lt '@{addDays(utcNow(), -7)}')
  or (ItemStatus eq 'Cancelled' and Modified  lt '@{addDays(utcNow(), -7)}')
```

There are 0 `Cancelled` rows today, so a single-clause version would have looked correct
until the first cancellation aged out.

Before the delete can be wired, `archiving-plan.md` needs three answers, one now settled:

1. ~~Is one month the right grace period?~~ **7 days, decided 2026-09-16.**
2. Should the sweep run nightly, weekly or monthly? — reopen against 7 days; the old
   "weekly is plenty" reasoning assumed a month.
3. Does the `Order` row need the same reconfirm rigor, or is deleting an order once
   all its units are gone safe to do immediately?

And the plan requires reconfirming each row against `Archive active.xlsx` **before**
deleting — read-only, the flow never writes to Excel. That reconfirm now exists as
`scripts/verify_archive_done_not_in_list.py` (match on unit id, confirm `Location = LI`
with a populated `Delivery Date`), though it is not wired into the flow.

### The `Modified` clock bug, and how it was closed

Worth keeping, because it is why the column changed. Stage C originally keyed on
`Modified`, so any pass touching Delivered/Cancelled rows reset the grace period on
exactly the rows it was waiting on — the sweep could be deferred forever with no error
anywhere. At 30 days that was a caution; a month absorbs an incidental touch. **At 7 days
it was live.** On 2026-09-16 every already-`Delivered` row sat within **1.5 days** of the
threshold — `E21010-1/2`, `E21010-2/2`, `E21014-1/1` within **0.4 days** — purely because
the 09-09/09-10 migration passes had touched them. Nothing had happened to the units: they
were delivered 62, 20 and 16 days earlier.

🔑 Keying on `DeliveryDate` removes it rather than guarding against it. No pass can change
when a delivery happened. Verified on the 11 rows retired 2026-09-16: `Delivery End Date`
matched `Archive active.xlsx`'s `Delivery Date` on all 11.

B1's `ItemStatus eq 'Active'` clause is still worth keeping — a touch costs a trigger-flow
run and a version — but it no longer props up another stage, and widening stage B can no
longer break the sweep. The one residue is `Cancelled`, above.
